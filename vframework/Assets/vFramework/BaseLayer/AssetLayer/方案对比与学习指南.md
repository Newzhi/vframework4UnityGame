# 方案对比与学习指南

> 本文是一份**学习路线**：通过对比 WindAssetBundle、ResKit、YooAsset 三套方案，理解资源框架怎么设计、怎么写、怎么一步步扩展到商业级能力。  
> 目标不是「要不要自己做」，而是**亲手做一遍，从能加载一个 prefab 走到热更上线**。

---

## 零、学习路线总览：四个阶段

把资源框架当成一门要练的技艺，分四阶递进。每一阶都有明确能力目标和参考方案：

```
阶段 1 · 读懂原理     →  本项目 WindAssetBundle（源码短、双层清晰）
阶段 2 · 亲手实现     →  按本文第六章，写出自己的 MVP
阶段 3 · 工程化打磨   →  借鉴 ResKit（释放习惯、模拟模式、多来源）
阶段 4 · 商业级扩展   →  借鉴 YooAsset（热更、下载、标签、多 Package）
```

| 阶段 | 你能做什么 | 对标能力 |
|------|------------|----------|
| **1 读懂** | 说清 Load 一条调用链里发生了什么 | 能读 WindAssetBundle 源码 |
| **2 实现** | 同步加载 prefab，能打包、能卸载 | 自研框架 MVP |
| **3 工程化** | 异步、规则分包、双模式、单元释放 | 中小项目可上线 |
| **4 商业化** | 版本管理、CDN 下载、边玩边下、加密 | 手游热更全流程 |

**学习心态**：不要第一天就写下载器。每一阶都做出可运行的 Demo，再往上叠——商业级框架也是这样长出来的。

**本项目的角色**：阶段 1～2 的「教材」。代码量小、注释清晰，适合对照着写自己的版本。

## 一、用一个故事理解资源框架

想象一家**图书馆**：

```
读者（业务代码）：「我要《登录界面》这本书」
                ↓
前台（加载器）：查目录，发现书在 3 号书柜，且 3 号柜依赖 1 号柜的《材质大全》
                ↓
管理员（资源管理器）：1 号柜没人借过 → 派人取；3 号柜同理；把书交给读者，登记「借出 +1」
                ↓
读者用完还书 → 登记「借出 -1」→ 某柜无人借时，关柜清架（卸载 AB）
```

任何资源框架都在做这件事：

1. **编目**（打包期）：哪本书在哪个柜、书与书之间有什么依赖
2. **借书**（加载期）：读者只说书名，不用自己找柜子
3. **还书**（卸载期）：记清谁借的、何时能清架

三套方案只是「图书馆的管理编制」不同，核心流程一样。

## 二、三套方案各是什么性格？

### 2.1 本项目 WindAssetBundle ——「双层图书馆」

```
业务 → ResourceManager（管「书」） → BundleManager（管「书柜」） → 磁盘 .ab
```

| 特点 | 说明 |
|------|------|
| 性格 | 简洁、分层清晰、源码可读 |
| 打包 | `BuildSetting.xml` 规则：目录 + 后缀 + File/Directory/All 粒度 |
| 映射 | 自定义 `manifest.ab`（Asset 路径 → AB 名 + 逻辑依赖） |
| 加载 | `Load("Assets/.../TestUI.prefab")`，三种异步风格 |
| 释放 | 手动 `Unload`，引用归零后 `LateUpdate` 延迟清架 |
| 学习定位 | **阶段 1～2 首选教材**：读懂原理、动手实现 MVP |

**像什么**：自己设计的双人图书馆——一个人管书架编号，一个人管借还登记，职责分明。学框架从这里入手最省力。

### 2.2 QFramework ResKit ——「万能借书证」

```
业务 → ResLoader（本单元的借书证） → ResMgr（总馆） → Res 子类（不同书源）
```

| 特点 | 说明 |
|------|------|
| 性格 | 开发体验好、API 统一、防泄漏 |
| 打包 | 右键 Mark，一标一包；Simulation Mode 开发期免打 AB |
| 加载 | `LoadSync("资源名")`，不必记 AB 名 |
| 释放 | `ResLoader.Recycle2Cache()`，脚本销毁时一次还清 |
| 来源 | AB + Resources + 网络图 + 自定义 Res |
| 学习定位 | **阶段 3 重点参考**：释放习惯、模拟模式、统一 API 设计 |

**像什么**：总馆发借书证，每个脚本一张证，销毁时统一还书，不容易漏还。实现 MVP 后，优先把它的好习惯补进你的框架。

### 2.3 YooAsset ——「连锁图书馆 + 物流中心」

```
业务 → ResourcePackage → 版本/清单/下载器/文件系统 → AssetHandle
```

| 特点 | 说明 |
|------|------|
| 性格 | 商业级、热更全链路、工具链完整 |
| 打包 | 收集器面板 + PackRule + **标签**（按标签下载/首包） |
| 加载 | `LoadAssetAsync` → `AssetHandle`，必须 `Release()` |
| 热更 | 版本 → 更新清单 → 下载器 → 边玩边下，内置 |
| 学习定位 | **阶段 4 对标目标**：商业热更的完整形态，按需拆解吸收 |

**像什么**：连锁馆 + 物流——不只借书，还管从总部调货、版本回退、按区域配送。框架成熟后，对照它扩展热更链路。

### 2.4 一张表看清差异

| 维度 | WindAssetBundle | ResKit | YooAsset |
|------|-----------------|--------|----------|
| 复杂度 | ★★☆ | ★★☆ | ★★★★ |
| 热更下载 | 需自研 | 需自研 | 内置 |
| 业务入口 | 全局 Manager | 单元 ResLoader | ResourcePackage |
| 释放方式 | Unload 单个资源 | Recycle 整批 | Handle.Release |
| 分包策略 | XML 规则引擎 | 标记 | 规则 + 标签 |
| 建议学习顺序 | 第 1 个读 | 第 2 个读 | 第 3 个读 |

三套方案是**同一门课的三本参考书**，不是三选一。先读懂 WindAssetBundle，再带着问题去看 ResKit 和 YooAsset 补了什么。

## 三、不管选谁，底层都在做同五件事

无论哪套方案、无论哪个学习阶段，这五件事**缺一不可**。第一版可以简陋，但骨架要有。

### ① 编目（打包期产出映射表）

```
"Assets/UI/Login.prefab"  →  "ui/login.ab"
```

没有这张表，业务就得自己拼 AB 路径——框架就失去了意义。

**注意点**：
- 映射表在**打包时**生成，**运行时**只读
- 标识要稳定（推荐完整 Asset 路径）
- 格式可以先 JSON，后期再二进制压缩

### ② 借书不问柜号（业务只用稳定标识）

```csharp
// 业务永远这样写
Load("Assets/AssetBundle/UI/TestUI.prefab");

// 而不是
AssetBundle.LoadFromFile("???/testui.prefab.ab");
```

**注意点**：打包时开启 `DisableLoadAssetByFileName`，强制路径一致。

### ③ 依赖自动处理

加载 Login.prefab 时，框架应自动先加载它引用的 Icon.png、材质等，再加载依赖的 AB。

两套依赖要分清：

| 依赖类型 | 谁管 | 举例 |
|----------|------|------|
| 逻辑资源依赖 | 你的 Manifest | prefab 依赖的贴图 Asset |
| AB 包依赖 | Unity Platform Manifest | ui.ab 依赖 icon.ab |

**注意点**：打包期漏分析依赖 → 运行期粉红材质、缺贴图。

### ④ 引用计数（借了几本，还了几本）

```
Load   → ref++
Unload → ref--
ref==0 → 进入卸载队列，帧末真正卸载
```

**注意点**：
- 同资源多次 Load 应命中缓存，不重复 IO
- ref 归零后同帧再 Load，应能「复活」（从卸载队列移除）
- **Load 了一定要 Unload**，否则泄漏

### ⑤ 开发期 / 真机期双模式

| 模式 | 行为 |
|------|------|
| 开发期 | 直读 Assets，改资源立即生效 |
| 真机期 | 读真 AB |

业务 API 不变，只切换初始化参数。否则开发期每次改图都要打 AB，人都会疯。

## 四、实现一套框架要综合的七大要素

把你正在写的框架想象成盖房子，七根柱子撑起整栋楼——从 MVP 到商业版，都是给这七根柱子加厚度：

```
        ┌─────────────────────────────────────┐
        │  ⑥ 异步与驱动   ⑦ 热更与路径解析   │
        ├─────────────────────────────────────┤
        │  ④ 引用计数     ⑤ 双模式            │
        ├─────────────────────────────────────┤
        │  ① 打包规则     ② 映射表            │
        ├─────────────────────────────────────┤
        │  ③ 双层加载架构                     │
        └─────────────────────────────────────┘
                      地基：Unity AB 机制
```

### 要素 ① 打包规则（决定 AB 怎么切）

**要解决**：哪些资源进包？一个 AB 里放几个？热更粒度多大？

| 粒度 | 比喻 | 适用 |
|------|------|------|
| 一文件一包 | 每本书单独柜 | 常热更的 UI、单图 |
| 一目录一包 | 一个系列一个柜 | 图标、图集 |
| 一模块一包 | 整个分区一个柜 | 公共 Shader |

本项目用 XML 规则（`BuildSetting.xml`），YooAsset 用收集器 + PackRule + Tag，ResKit 用右键标记。

**实现建议（按学习阶段）**：
- 阶段 2：写死一条规则（某目录下 prefab 各打一包）
- 阶段 3：配置文件 + 最长前缀匹配（WindAssetBundle 思路）
- 阶段 4：加标签（YooAsset 思路，支持按模块下载）

**易错点**：规则盖不住依赖资源 → 打包直接报错或运行缺资源。

---

### 要素 ② 映射表 / Manifest（运行时查表）

打包产出，运行时读取：

```
Resource 索引：  0 = Login.prefab, 1 = Icon.png, ...
Bundle 映射：    login.ab 含 [0],  icon.ab 含 [1]
依赖链：         Login.prefab 依赖 [1, ...]
```

本项目打成 `manifest.ab` 里三份 bytes；你也可以先用 JSON。

**实现建议**：`IManifestWriter`（Editor）和 `IManifestReader`（Runtime）成对设计，格式迭代时不扯皮。阶段 2 用 JSON，阶段 3 再压缩二进制。

**易错点**：清单版本和 AB 文件版本不一致（热更大忌）。

---

### 要素 ③ 双层加载架构（最推荐保留的设计）

```
Resource 层（逻辑）    按 Asset 路径，业务面对的层
    ↓
Bundle 层（物理）      按 AB 文件名，只管 LoadFromFile
```

**为什么分两层？**

- 业务关心「我要 Login 界面」，不关心它在 `login.ab` 还是 `ui_pack.ab`
- AB 的加载、依赖、缓存和 Asset 对象的缓存是两种生命周期
- 以后换分包策略，只改映射表，不改业务代码

WindAssetBundle 的 `ResourceManager` + `BundleManager` 是教科书式拆分。ResKit 合在 Res 体系里，YooAsset 用 Provider + BundleHandle，本质仍是两层，只是命名不同。

**推荐写法思路**：

```
Load(assetKey)
  → 查映射表得 bundleName
  → BundleMgr.Load(bundleName)      // 含 AB 间依赖
  → 查逻辑依赖，递归 Load 依赖 Asset
  → bundle.LoadAsset(assetKey)
  → 包装成 IResource 返回
```

---

### 要素 ④ 引用计数与释放策略

三种成熟释放风格：

| 风格 | 代表 | 特点 |
|------|------|------|
| 单个释放 | WindAssetBundle `Unload(res)` | 精确，但业务要记得卸 |
| 单元批量释放 | ResKit `ResLoader.Recycle()` | 脚本销毁时一次还清，省心 |
| 句柄释放 | YooAsset `handle.Release()` | 每次加载必有句柄，最严格 |

**推荐写法（阶段 3 融合 ResKit 习惯）**：

```csharp
// 对外：单元 Loader（借鉴 ResKit）
class ResLoader {
    List<IResource> m_List;
    IResource Load(key) { var r = Mgr.Load(key); m_List.Add(r); return r; }
    void Recycle() { foreach (var r in m_List) Mgr.Unload(r); }
}

// 对内：全局 Manager + 延迟卸载（借鉴 WindAssetBundle）
// ref==0 → 进队列 → LateUpdate 真正 Unload
```

**易错点**：
- 切换贴图只 Load 不 Unload → 内存涨
- 销毁 GameObject 不等于 Unload 资源引用
- 依赖资源的 ref 要随主资源一起减

---

### 要素 ⑤ 双模式（开发期生命线）

```csharp
Initialize(new Context {
    SimulationMode = true,   // 开发：AssetDatabase 直读
    // SimulationMode = false,  // 真机：读 AB
});
```

ResKit 叫 Simulation Mode，YooAsset 叫 EditorSimulateMode，本项目叫 `editor: true`。

**实现要点**：Mode 切换只影响「数据从哪读」，不影响 Load API 签名——阶段 2 就应把接口设计好。

---

### 要素 ⑥ 异步与帧驱动

同步加载最简单，但大卡会卡主线程。异步有三种做法：

| 做法 | 代表 | 要点 |
|------|------|------|
| 轮询 Update | WindAssetBundle | 每帧检查 AsyncOperation.isDone |
| 加载队列 | ResKit | Add2Load 一批，再 LoadAsync |
| Operation 对象 | YooAsset | 返回可 yield 的 Operation |

**共同要求**：异步就要有「推进器」——`Update()` 或协程/await 挂起。

WindAssetBundle 还要求 `LateUpdate()` 做延迟卸载，别忘了。

**实现建议**：阶段 2 先同步；阶段 3 加协程 `yield return`；阶段 4 再加 await / Operation。

---

### 要素 ⑦ 路径解析与热更扩展

```csharp
// 把「逻辑名 → 磁盘路径」外置
string Resolve(string name) {
    var hot = $"{persistentData}/{name}";
    if (File.Exists(hot)) return hot;
    return $"{streamingAssets}/{name}";
}
```

YooAsset 把这扩展成多文件系统（Builtin + Cache + Web）。你 MVP 阶段一个委托就够，但**接口要预留**。

热更完整链路（v3 再做）：版本号 → 拉清单 → 对比差异 → 下载 → 校验 → 加载。

## 五、分模块怎么写：思路而非照抄

### 5.1 资源模块（Resource）——「借出去的那本书」

**要定义什么：**

| 定义 | 作用 | 最小实现 |
|------|------|----------|
| `IResource` | 业务持有的句柄 | url + GetAsset + Instantiate |
| `ResourceBase` | 引用计数、状态、依赖数组 | ref、bundle、dependencies |
| `ResourceSync` | 同步加载 | Load → LoadAsset → done |

**写法顺序**：

1. 先写 `IResource` 接口（定对外长什么样）
2. 再写 `ResourceBase`（加 ref、依赖、状态机）
3. 最后写 `ResourceSync`（真正调 Bundle 层）

**状态机（心里要有这张图）**：

```
Waiting → Loading → Ready → PendingUnload → Disposed
                         ↑______同帧再 Load 可复活______|
```

---

### 5.2 加载器模块（Loader）——「图书馆前台 + 馆长」

分两个角色：

#### 角色 A：全局 Manager（馆长）

```csharp
interface IResourceMgr {
    void Initialize(Context ctx);
    void Update();       // 推异步
    void LateUpdate();   // 做卸载
    IResource Load(string assetKey, bool async);
    void Unload(IResource res);
}
```

内部维护：
- `Dictionary<assetKey, Resource>` 缓存
- `Manifest` 映射
- 卸载延迟队列

#### 角色 B：单元 ResLoader（借书证，可选但强烈推荐）

```csharp
interface IResLoader {
    IResource LoadSync<T>(string key);
    void Recycle();  // OnDestroy 时调用
}
```

**为什么推荐 ResLoader？**  
新手最容易忘 Unload。单元 Loader 把「释放」绑在脚本生命周期上，和 ResKit 一样省心。

#### 角色 C：BundleMgr（管书柜的人，内部）

```csharp
interface IBundleMgr {
    Bundle Load(string bundleName, bool async);
    void Unload(Bundle bundle);
}
```

业务永远见不到这一层——这是刻意设计。

---

### 5.3 打包器模块（Builder）——「编目员」

**流水线就六步，按顺序写：**

```
① Collect      按规则扫文件
② AnalyzeDep   GetDependencies，带出依赖
③ Group        按规则算每个资源属于哪个 AB
④ WriteManifest 输出映射表 + 依赖表
⑤ BuildAB      调 BuildPipeline.BuildAssetBundles
⑥ Clean        删过期 AB（可选，但建议有）
```

**每步一个类**，不要全塞一个 `Builder.cs`——以后改规则、改 Manifest 格式才不痛苦。

**打包器自检**（打完后人工看一遍）：

- [ ] 输出目录有平台 Manifest + 你的映射文件
- [ ] 随机挑一个 prefab，它的依赖资源都在映射表里
- [ ] AB 数量和预期一致，没有 0 字节文件
- [ ] 改一个资源后 AB hash 变了（确定性构建）

## 六、动手路线：按周迭代（阶段 2 → 3 → 4）

对应第四章的七大要素，按周推进。每周结束都应有一个**能跑起来的 Demo**，而不是一堆写了一半的类。

### 第 1 周：能加载一个 Cube

| 做 | 不做 |
|----|------|
| 写死 1 条打包规则 | 异步 |
| JSON 映射表 | 二进制 Manifest |
| BundleMgr 同步加载 | 热更 |
| ResourceMgr 同步 Load | ResLoader |

**验收**：真机上 `Load("Assets/Demo/Cube.prefab").Instantiate()` 出现立方体。

### 第 2 周：能加载、能卸载、不泄漏

| 做 | 不做 |
|----|------|
| 引用计数 + LateUpdate 延迟卸载 | 下载器 |
| 依赖分析 CollectDependency | 多 Package |
| editor 双模式 | 加密 |
| ResLoader + Recycle | |

**验收**：反复 Load/Unload 10 次，内存不持续增长；prefab 依赖的材质正常。

### 第 3 周：开发效率 + 异步

| 做 |
|----|
| XML/ScriptableObject 打包规则 |
| 协程异步 Load + Update 驱动 |
| 清理过期 AB |
| 代码生成资源路径常量（可选） |

**验收**：改 XML 规则后重打 AB，UI 和 Icon 按预期分包；异步加载 UI 不卡死。

### 第 4 周及以后：阶段 4 · 商业级扩展

对照 YooAsset，逐项扩展你的框架：

| 能力 | 学什么 | 参考 |
|------|--------|------|
| 热更路径 | persistent 优先于 streaming | YooAsset 文件系统 |
| 版本与清单 | 远端 version → 拉取清单 diff | YooAsset HostPlayMode |
| 下载器 | 按标签批量下载、断点续传 | YooAsset Downloader |
| 标签分包 | 首包只拷指定 Tag | YooAsset Collector Tag |
| 句柄释放 | 每次 Load 返回 Handle，必须 Release | YooAsset AssetHandle |
| 加密 | 打包加密 + 运行时解密插件 | YooAsset IBundleEncryptor |
| 可观测性 | 构建报告、泄漏检测 | YooAsset 分析器 |

每加一项，单独写 Demo 验证，再并入主线——商业框架也是这样渐进演进的。

## 七、各学习阶段参考谁

学习不是从零发明，而是**站在三套方案的肩膀上**，按阶段吸收：

| 学习阶段 | 你要练的能力 | 优先参考 | 原因 |
|----------|--------------|----------|------|
| 阶段 1 读懂 | 双层架构、映射表、依赖链 | **WindAssetBundle** | 源码短，双层一目了然 |
| 阶段 2 实现 | 打包六步、同步 Load/Unload | **WindAssetBundle** | 与本项目一一对应，便于对照 |
| 阶段 3 工程化 | 单元释放、模拟模式、异步 | **ResKit** | 开发体验设计成熟 |
| 阶段 3 工程化 | 规则分包、Manifest 设计 | **WindAssetBundle** | XML 规则引擎清晰 |
| 阶段 4 商业化 | 热更、下载、标签、多 Package | **YooAsset** | 商业链路完整，拆模块学 |

**学习顺序**：WindAssetBundle（读懂+实现）→ ResKit（补工程习惯）→ YooAsset（扩展商业能力）。跳步也能学，但容易「会用不懂原理」——先把阶段 1～2 走扎实。

## 八、最易翻车的十个坑

| # | 坑 | 现象 | 预防 |
|---|-----|------|------|
| 1 | 规则盖不住依赖 | 打包报错或运行粉红 | 打包期分析全依赖，规则兜底 |
| 2 | 路径不一致 | Load 找不到资源 | 统一用完整 Asset 路径 |
| 3 | 忘了 Update/LateUpdate | 异步永不完成 / 资源不卸 | 常驻 MonoBehaviour 驱动 |
| 4 | 只 Load 不 Unload | 内存持续上涨 | ResLoader 或严格配对 |
| 5 | 销毁 GO 不卸资源 | AB 卸不掉 | GO 销毁 ≠ 资源 ref-- |
| 6 | 清单与 AB 版本不一 | 热更后乱套 | 清单和 AB 同一次构建产出 |
| 7 | 平台打错 AB | 安卓跑 Windows 包 | Build Target 与运行平台一致 |
| 8 | 同步加载大卡 | 卡顿 | 大资源走异步 |
| 9 | 同帧卸了又 Load | 未复用缓存 | 延迟卸载（LateUpdate） |
| 10 | 阶段 4 的能力阶段 2 就做 | 永远写不完、学不会 | 严格按学习阶段递进 |

## 九、写代码前的设计 checklist

动手写第一行代码前，在纸上或白板填完这张表：

```
□ 资源标识用什么？        → 推荐：完整 Asset 路径
□ 分包粒度？              → 先 File，后按需 Directory
□ 映射表格式？            → MVP 用 JSON
□ 分几层？                → Resource + Bundle 双层
□ 业务怎么释放？          → ResLoader.Recycle
□ 开发期怎么调试？        → SimulationMode
□ 异步怎么推？            → 先同步，后 Update 轮询
□ 路径怎么解析？          → Func<string,string> 预留热更
□ 依赖谁负责？            → 打包分析 + 运行时自动递归 Load
□ 第一版验收标准？        → 1 个 prefab 加载并 Instaniate 成功
```

全部有答案，再建工程文件夹。

## 十、推荐目录结构（照着建文件夹）

```
YourFramework/
├── Editor/
│   ├── Config/           BundleBuildConfig, Rule
│   ├── Pipeline/         Collector, Analyzer, Grouper, ManifestWriter, Builder
│   └── Menu/             一键打包菜单
└── Runtime/
    ├── API/              IResource, IResLoader
    ├── Resource/         ResourceBase, Sync, Async, Editor
    ├── Bundle/           BundleBase, Sync, Async
    ├── Manager/          ResourceMgr, BundleMgr
    ├── Manifest/         IManifestReader, AssetManifest
    └── Init/             ResourceInitContext, IFileResolver
```

**原则**：`Runtime/API` 是业务唯一能 import 的命名空间，其余 `internal`。

## 十一、最小 MVP：12 个类型就够跑通

| # | 类型 | 一句话 |
|---|------|--------|
| 1 | `IResource` | 业务句柄 |
| 2 | `ResourceBase` | ref + 依赖 + 状态 |
| 3 | `ResourceSync` | 同步实现 |
| 4 | `BundleBase` | AB 封装 |
| 5 | `BundleSync` | LoadFromFile |
| 6 | `IResourceMgr` | 全局 Load/Unload |
| 7 | `ResourceMgr` | 缓存 + 延迟卸载 |
| 8 | `BundleMgr` | AB 缓存 + Manifest 依赖 |
| 9 | `IManifestReader` | 读映射表 |

| 11 | `AssetBundleBuilder` | 六步流水线 |
| 12 | `IFileResolver` | 路径解析 |

其余（Async、ResLoader、加密、下载器）都是迭代项。

## 十二、总结：从学习到商业的完整思路

用一句话收束全文：

> **打包期编好目录，运行期读者只报书名，图书馆负责找柜、借依赖、记册数、帧末清架；开发期允许不走物流（直读 Assets），真机期才走正式库房（AB）。**

三家方案是这门课的**三本教材**，对应不同学习阶段：

| 教材 | 阶段 | 你带走的能力 |
|------|------|--------------|
| **WindAssetBundle** | 1～2 | 原理清晰、能自己写 MVP |
| **ResKit** | 3 | 好用的 API、不易泄漏的释放模型 |
| **YooAsset** | 4 | 热更、下载、标签、多平台商业链路 |

**完整学习路径**：

```
读懂 WindAssetBundle
    → 亲手实现 MVP（同步加载 + 打包 + 卸载）
    → 吸收 ResKit（ResLoader、模拟模式、异步）
    → 扩展 YooAsset 模块（版本、下载、标签、加密……）
    → 你的框架具备商业项目能力
```

不要跳步，但也不必停步——每一阶的 Demo 跑通了，就值得进入下一阶。
